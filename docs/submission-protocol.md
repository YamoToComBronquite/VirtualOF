# Confirmação e reenvio de mensagens

Contrato do servidor para o agente de interface:

- Cada novo envio `task` ou `command` deve trazer um `requestId` único (UUID recomendado; string não vazia com até 128 caracteres). O mesmo ID identifica o mesmo envio, com texto, destino e anexos imutáveis. Um novo pedido usa outro ID.
- O servidor responde somente ao socket remetente com `{ type: 'submission', requestId, accepted, serverId }`. `accepted: true` significa que o pedido foi registrado e será executado; não significa conclusão ou sucesso da tarefa. Falhas posteriores aparecem no log e nos estados do agente/plano, sem transformar o aceite em recusa.
- O registro do aceite ocorre antes da confirmação e da execução. Repetir um ID aceito retorna `accepted: true, duplicate: true`, sem executar novamente, salvar anexos ou criar outro registro de usuário. Isso vale durante e após a tarefa, mesmo se o histórico visível já tiver sido reduzido. O conteúdo de uma repetição é ignorado: não reutilize o ID para conteúdo diferente.
- Recusas anteriores ao aceite respondem `accepted: false` e `text`; não reservam o ID. Preserve o rascunho. É possível tentar novamente com o mesmo ID e o mesmo pedido após resolver a recusa.
- Se o composer foi editado antes da recusa, preserve a tentativa original separadamente, sem sobrescrever as novas edições. Permita reenviar a original ou descartá-la explicitamente. Um registro `user` no log não é confirmação de aceite: uma falha ao registrar a mensagem pode ocorrer antes de o ID ser aceito. Após reconectar, consulte o registro de aceite mesmo quando o ID aparecer no histórico.
- Se a confirmação se perder, mantenha o ID e o rascunho. Ao reconectar, consulte `{ type: 'submission-status', requestId }`. A resposta é `{ type: 'submission-status', requestId, accepted, serverId }`. A consulta não executa tarefas. Com aceite confirmado, a interface pode limpar somente o rascunho correspondente; sem aceite, pode repetir o pedido completo usando o mesmo ID.
- `snapshot.serverId` identifica a instância do servidor. Os IDs aceitos ficam em memória durante toda essa instância, sem expiração e independentemente do log. Após reiniciar o servidor, `serverId` muda e o registro é perdido: não reenvie automaticamente um pedido de resultado incerto entre instâncias. Preserve o rascunho e informe a incerteza ao usuário. Não há garantia de execução única entre reinícios.
- Clientes antigos sem `requestId` continuam funcionando, mas sem consulta ou proteção contra duplicação. A interface atualizada deve sempre usar o ID e comparar o `serverId` anterior com o da reconexão.
